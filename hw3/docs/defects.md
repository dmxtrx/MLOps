# Разбор дефектов — ДЗ 3

Пять заложенных дефектов и три сопутствующие правки. Для каждого — где сидел,
чем выдавал себя, как исправлен и каким числом это подтверждается. Данные —
MedMCQA: v1 — 3000 строк из train, v2 — те же плюс 319 строк из validation.

## 1. Данные попадали в git

**Где был.** Три дыры сразу. В корневом `.gitignore` не было `data/`. В
`dvc.yaml` у стадии `split` в `outs` был объявлен только `data/train.jsonl`:
из пяти артефактов `params.paths` под DVC жили три (`raw`, `clean`, `train`),
а `val.jsonl` и `test.jsonl` — нет. И не был настроен remote: выгружать данные
было некуда.

**Как проявлялся.** DVC дописывает в `data/.gitignore` только объявленные
`outs`. `val.jsonl` и `test.jsonl` туда не попадали, и `git add .` забирал их
в индекс — `git log --stat` показывал крупные JSONL. Никакой ошибки при этом
нет: пайплайн отрабатывает, коммит проходит.

**Как исправлен.** `data/` добавлен в `.gitignore` вместе с `.venv/`,
`__pycache__/`, `.DS_Store`, `*.bak`, `*.orig`. В `outs` стадии `split`
объявлены все три сплита. Настроен локальный remote
(`dvc remote add -d local ../dvc-remote`). Файлы источника заведены через
`dvc add sources/medmcqa` — в git лежит только `sources/medmcqa.dvc`.

**Чем подтверждается.** Проверка 1: `git ls-files data/` — 0 файлов, `data/`
есть в `.gitignore`, remote `local` настроен по умолчанию, в `outs` объявлены
все пять путей из `params.paths` (было три из пяти). Проверка 8: в git нет
файлов тяжелее 5 МБ.

## 2. `dvc repro` не замечал смену версии

**Где был.** В `dvc.yaml` цепочка рвалась в двух местах. У стадии `collect`
не было секции `params`: версия и список источников живут в `params.yaml`, а
DVC отслеживал только код стадии — правку `collect.version` он не видел. У
стадии `clean` в `deps` не было `data/raw.jsonl`: даже пересобрав его, DVC не
считал `clean` зависящей от него.

**Как проявлялся.** `make v2` запускал `dvc repro`, тот сообщал, что всё
актуально, и в `data/` оставались артефакты прошлой версии. Опасно это
тишиной: файлы и метрики выглядят свежими, но относятся к v1.

**Как исправлен.** `collect` получил `params: [collect, paths.raw,
paths.metrics_collect]`, а в `deps` — путь к источнику `sources/medmcqa` (это
и был `TODO`). У `clean` в `deps` добавлен `data/raw.jsonl`. Заодно
`metrics/collect.json` объявлен метрикой, чтобы счётчики сбора были видны в
`dvc metrics diff`.

**Чем подтверждается.** Проверка 4 переключает версию и сравнивает хеши
`clean.jsonl`: v1 `50e0acf7` (3000 строк на входе очистки) → v2 `7cfff826`
(3319 строк). Стадия пересчиталась, и вход вырос ровно на вклад validation —
319 строк.

## 3. Контаминация train/test

**Где был.** `src/split.py` резал датасет функцией `row_split`: случайная
перестановка строк и нарезка по долям. Ключ группы `split.group_key`
фактически не использовался. Выдавал это словарь `sizes` — он считался по
группам и нигде не применялся.

**Как проявлялся.** Вопросы одной темы разъезжались по train и test. В нашем
формате тема дословно входит в промпт (`Subject: …`, `Topic: …`), а вопросы
внутри темы близки по содержанию: модель видела на обучении почти тот же
вопрос, что потом в test. Пайплайн при этом не падал — `split` только
записывал сводку в метрики.

Тот же сплит, воспроизведённый на очищенном v2 (перестановка с `seed = 42`,
нарезка 80/10/10 по строкам):
**[ЗАПОЛНИТЬ: вывод скрипта — id / текст / группы / near-dup]**.

**Как исправлен.** `row_split` заменён на `group_split`: метки получают
группы, а не строки, и тема целиком уходит в один сплит. Группы
перемешиваются с `seed`, затем каждая отправляется в тот сплит, которому
сильнее всего недостаёт до своей доли, — так доли по строкам держатся возле
80/10/10, а не «train 90 %, test пуст». В конец стадии добавлен гейт:
ненулевое пересечение на любом из четырёх уровней роняет `split` с
перечислением счётчиков.

Групповой сплит сам по себе обнуляет только пересечение групп. Пересечения
по тексту и near-dup-пары уходят в ноль, лишь когда дубли схлопнуты до
сплита, — поэтому этот дефект закрывается только вместе с дефектом 4.

**Чем подтверждается.** Проверка 5 (`scripts/check_contamination.py`): 0 на
всех четырёх уровнях — id, текст, группы, near-dup-пары. Фактические доли
сплитов: **[ЗАПОЛНИТЬ: ratios_actual из metrics/split.json]**.

## 4. Почти-дубли переживали очистку

**Где был.** `src/clean.py`, шаг 5: вместо дедупликации стояла заглушка
`near: set[int] = set()`. Функция `near_duplicates` в `src/dedup.py` была
написана, но нигде не вызывалась. Работала только точная дедупликация по
нормализованному тексту вопроса.

**Как проявлялся.** Тот же вопрос с другой пунктуацией, другой нумерацией
вариантов («0.» против «0)») или переставленными вариантами проходил
очистку: нормализованные строки различаются, и точное сравнение их не
ловит. `dropped_near_dup` в метриках был нулём при любом входе.

**Как исправлен.** После точной дедупликации запускается MinHash + LSH по
нормализованному тексту вопроса с параметрами из `clean.near_dup`: шингл —
4 слова, 64 перестановки, порог Жаккара 0.85. Точная идёт первой — дешёвая
операция снимает основную массу, MinHash работает по остатку. Порог совпадает
с `contamination.threshold`, поэтому проверка контаминации меряет
пересечения, а не разницу порогов.

**Чем подтверждается.** Проверка 2 на подложенном наборе: точный дубль снят
(`dropped_exact_dup = 1`), почти-дубль тоже (`dropped_near_dup = 1`). На
MedMCQA v2 очистка убрала 6 строк из 3319, осталось 3313:
**[ЗАПОЛНИТЬ: dropped_length / dropped_exact_dup / dropped_near_dup из metrics/clean.json]**.

## 5. Гейт разнообразия пропускал вырожденный набор

**Где был.** `src/diversity.py`: при нарушенных порогах стадия печатала
«предупреждение» одной строкой через «; » и завершалась с кодом 0.

**Как проявлялся.** Набор из 1200 строк с одним системным промптом, одной
темой и ответами одной длины проходил весь пайплайн. DVC видел успешный код
возврата и шёл дальше. Отчёт, который никого не останавливает, — не гейт.

**Как исправлен.** При любом нарушении стадия завершается через `SystemExit`
с кодом 1 и перечисляет нарушенные пороги, каждый отдельной строкой — с
фактическим значением и порогом. Метрики записываются до падения, так что по
`metrics/diversity.json` видно, что именно не прошло. Отдельные строки — не
косметика: проверка 6 считает строки через `grep -c`, и склеенные через «; »
нарушения засчитались бы за одно.

**Чем подтверждается.** Проверка 6: на вырожденном наборе гейт падает. По
построению набора нарушены 6 порогов из 7 — все, кроме числа примеров;
проверка по своим ключевым словам засчитывает 4. Проверка 7: на MedMCQA v2
гейт открыт — 3313 строк, 5 системных промптов, 1081 группа, крупнейшая
занимает 1.9 %, разброс длин ответа p90/p10 = 2.62. Пороги не снижались.

## Сопутствующие правки в `dvc.yaml`

К пяти заложенным дефектам не относятся, найдены по ходу работы:

- У `clean` в `deps` не было `src/stats.py`, хотя `clean.py` импортирует из
  него `percentile`: правка персентилей не пересчитала бы очистку.
- `split` берёт `shingle_words` и `num_perm` из `clean.near_dup`, но эту
  секцию не отслеживал. Добавлена в `params` стадии.
- `split` теперь зависит от `metrics/diversity.json`. Без этого ребра
  `diversity` и `split` — соседи, оба зависят только от `clean.jsonl`, и DVC
  вправе выполнить сплит раньше гейта: упавший гейт не остановил бы уже
  нарезанный train.
