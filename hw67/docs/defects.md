# Часть A. Найденные дефекты и их исправления

Стартовый проект содержал четыре дефекта, каждый из которых по отдельности
делал пайплайн «sweep → выбор → реестр → оценка» нерабочим или ложным.

## 1. Смешивание runs: все кандидаты логировались в один run

**Где:** `src/sweep.py`, `main()`.

**Симптом:** все шесть конфигураций обучались внутри одного nested-run
`all-candidates`. Метрики `val_loss` шести разных обучений записывались в одну
метрическую историю общего run; `log_params` срабатывал только для первого
кандидата (строка `if not mlflow.get_run(...).data.params` молча пропускала
параметры остальных пяти); `samples.json`, модель и артефакты каждого
следующего кандидата перезаписывали предыдущие.

**Чем грозило:** 6 конфигураций → 1 run вместо 6. Выбрать лучшего кандидата
невозможно: `select()` в `src/promote.py` ищет отдельные runs с тегом
`kind=candidate` и упал бы с «Число отдельных runs не совпадает с
конфигурациями». Проверка 1 (`минимум шесть отдельных законченных runs`)
не проходит.

**Исправление:** каждый кандидат — отдельный дочерний run родителя `sweep`:

```python
with mlflow.start_run(run_name="sweep", tags={"kind": "sweep", **versions}) as parent:
    for candidate in p["sweep"]:
        with mlflow.start_run(run_name=candidate["name"], nested=True):
            rows.append(run_candidate(p, candidate, versions))
```

## 2. Потеря артефактов: volume объявлен, но не примонтирован

**Где:** `compose.yaml`, сервис `mlflow`.

**Симптом:** сервер стартовал с `--artifacts-destination=/mlartifacts`, но
каталог `/mlartifacts` оставался внутри слоя контейнера: named volume
`artifacts` был объявлен в секции `volumes:` файла, однако к сервису не
примонтирован.

**Чем грозило:** при пересоздании контейнера (обновление образа, `--force-recreate`,
перезапуск Docker) все загруженные артефакты — адаптеры LoRA, логged-модели,
таблицы — исчезали вместе с контейнером, хотя в Postgres оставались ссылки на
них. Проверка 8 (`make check-storage`, пересоздание контейнера и повторное
скачивание probe-артефакта) теряла файл.

**Исправление:**

```yaml
  mlflow:
    # ... command: --artifacts-destination=/mlartifacts
    volumes:
      - artifacts:/mlartifacts
```

## 3. Нет версий данных: хеши train/val выбрасывались из provenance

**Где:** `src/sweep.py`, `main()`.

**Симптом:** `provenance()` честно считает `data_train_sha256` и
`data_val_sha256`, но sweep отфильтровывал их:
`versions = {k: v for k, v in provenance(p).items() if not k.startswith("data_")}`.

**Чем грозило:** runs не фиксировали, на каких данных обучены, — воспроизводимость
и отслеживаемость терялись. А `select()` при promote требует от каждого run теги
`data_train_sha256`/`data_val_sha256`, совпадающие с текущими файлами, поэтому
любой выбор кандидата заканчивался бы `ValueError: отсутствует или устарел
data_train_sha256; повторите sweep`. Проверка 2 (версии кода, данных, конфига,
базы) не проходит.

**Исправление:** `versions = provenance(p)` — версии данных логируются в теги
родителя и каждого кандидата.

## 4. Обход порога: gate написан, но не вызывался

**Где:** `src/promote.py`, `promote()`.

**Симптом:** функция `gate()` проверяет конечность метрик, статус run и
отношение `final_val_loss / base_val_loss` к порогу `max_val_ratio`, но
`promote()` её не вызывал: ratio считался вручную «для тега», после чего
модель регистрировалась в реестре при любом val loss — сразу ставились тег
`validation: passed` и alias `champion`.

**Чем грозило:** кандидат, ухудшивший val loss относительно базы
(ratio > 1.0), попадал в реестр как «прошедший валидацию». Порог существовал
только на бумаге; проверка 6 (`promote(..., max_val_ratio=0.0)` обязан бросить
ValueError) падала, потому что нулевой порог «проходил» любой положительный loss.

**Исправление:** первой строкой `promote()` вызывается
`ratio = gate(run, threshold)`, и только после успешной проверки выполняются
`register_model`, теги `val_ratio` / `gate.max_val_ratio` / `validation` и alias.
Проверено: `promote(..., 0.0)` отклоняет лучшего кандидата с ValueError,
реестр при этом не изменяется.
